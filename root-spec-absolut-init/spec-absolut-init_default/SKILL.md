# /spec-absolut-init — Абсолютная спецификация проекта

Генерирует и поддерживает в актуальном состоянии **полную техническую документацию** проекта в `specification/absolut/`, организованную по **бизнес-функциональностям**.
Документация предназначена для использования AI-агентом при дальнейшей разработке, поэтому содержит максимально точные и структурированные факты из кода.

---

## Назначение

Абсолютная спецификация — это **единый источник правды** о текущем состоянии проекта, извлечённый из кода и организованный по бизнес-функциям. Она отвечает на вопросы:

- Что делает конкретная бизнес-функциональность?
- Какие API-эндпоинты обслуживают эту функциональность?
- Какие таблицы БД задействованы?
- Какие сервисы, DTO, валидации, интеграции с ней связаны?
- Какие бизнес-правила и ограничения действуют?

---

## Вход / выход

- **Вход:** корень репозитория проекта; аргумент — имя бизнес-функциональности (например, `receive`, `write-off`, `impairment`, `auth`, `payments`) или `all`.
- **Выход:** файлы в `specification/absolut/<функциональность>/` + обновлённые `index.md`.

```
specification/absolut/

├── <функциональность-1>/

│   ├── api.md                            # Эндпоинты, связанные с функциональностью
│   ├── business.md                       # Сервисы, правила, валидация, статусы
│   ├── db.md                             # Таблицы, колонки, связи
│   ├── data-model.md                     # DTO, Entity, Enum, связанные с функциональностью
│   ├── rest-integration.md               # Внешние HTTP-вызовы (Feign, RestTemplate и т.д.)
│   ├── kafka-integration.md              # Kafka-топики: producers и consumers
│   └── scheduler.md                      # Планировщики, cron-задачи
├── <функциональность-2>/
│   ├── index.md
│   ├── api.md
│   ├── business.md
│   ├── db.md
│   ├── data-model.md
│   ├── rest-integration.md
│   ├── kafka-integration.md
```

> **Гибкость:** не все файлы внутри раздела обязательны. Создавай только те, для которых найдены данные в коде. Если у функциональности нет API (внутренний процесс) — `api.md` не создаётся. Если нет REST-интеграций — `rest-integration.md` не создаётся. Если нет Kafka — `kafka-integration.md` не создаётся. Если нет планировщиков — `scheduler.md` не создаётся.

## Как определить бизнес-функциональность

Скилл получает имя функциональности от пользователя. Для поиска связанного кода:

1. **По имени:** ищи пакеты, классы, методы, содержащие имя функциональности или его синонимы (например, `receive` → `receiv`, `reception`, `incoming`).
2. **По контроллерам:** найди контроллеры/роутеры с эндпоинтами, относящимися к функциональности.
3. **По сервисам:** найди сервисы, реализующие бизнес-логику функциональности.
4. **По цепочке зависимостей:** от контроллера → к сервису → к репозиторию → к entity → к таблице БД. Собери всю цепочку.
5. **По DTO:** найди DTO, используемые в эндпоинтах и сервисах функциональности.
6. **По интеграциям:** найди внешние вызовы и события (Kafka, HTTP-клиенты), инициируемые из сервисов функциональности.

При вызове с `all`:
1. Просканируй все контроллеры/роутеры и сервисы проекта.
2. Сгруппируй их по бизнес-функциональностям (по пакетам, именам, доменной принадлежности).
3. Сгенерируй раздел для каждой обнаруженной функциональности.

## Алгоритм выполнения

### Фаза A — Анализ проекта

1. **Определи технологический стек:** прочитай файлы сборки (`pom.xml`, `build.gradle`, `package.json`, `Cargo.toml`, `requirements.txt`, `go.mod`, `*.csproj` и т.д.). Определи язык, фреймворк, СУБД, брокер сообщений, инструмент миграций.
2. **Определи структуру проекта:** просканируй дерево каталогов. Определи расположение контроллеров, сервисов, репозиториев, сущностей, DTO, конфигураций, миграций.
3. **Проверь существующую спецификацию:** просканируй `specification/absolut/` — определи какие разделы уже существуют.

### Фаза B — Идентификация функциональности

Если аргумент — **имя функциональности:**
1. Ищи код, связанный с этой функциональностью: по именам пакетов, классов, методов, эндпоинтов.
2. Проследи цепочку: контроллер → сервис → репозиторий → entity → таблица БД.
3. Собери все связанные DTO, Enum, интеграции, валидаторы.

Если аргумент — `all`:
1. Просканируй все контроллеры/роутеры проекта.
2. Сгруппируй по бизнес-функциональностям (по пакетам, доменам, именам).
3. Выполни Фазу B для каждой обнаруженной функциональности.

### Фаза C — Сбор данных (read-only)

Для каждой функциональности собери данные для всех файлов:

1. **api.md:** контроллеры/роутеры — эндпоинты, параметры, типы запросов/ответов, авторизация.
2. **business.md:** сервисы (интерфейсы + реализации), валидаторы, бизнес-правила из условий и исключений, статусы.
3. **db.md:** SQL-миграции и ORM-сущности для задействованных таблиц, FK, индексы.
4. **data-model.md:** Entity, DTO, Enum, маппинг между ними.
5. **rest-integration.md:** HTTP-клиенты (Feign, RestTemplate и т.д.), вызываемые из сервисов функциональности.
6. **kafka-integration.md:** Kafka producers и consumers, связанные с функциональностью.
7. **scheduler.md:** планировщики (@Scheduled, Quartz, cron), связанные с функциональностью.

> **Важно:** читай файлы исходного кода напрямую. Не делай предположений — документируй только то, что подтверждено кодом.

### Фаза D — Генерация документации

1. Создай директорию `specification/absolut/<функциональность>/` если не существует.
2. Сгенерируй файлы по шаблонам. Создавай только файлы, для которых найдены данные.
3. В каждом файле укажи **источник** (относительный путь к файлу кода) для ключевых фактов.
4. Создай/обнови `index.md` раздела со ссылками на фактически созданные файлы.

### Фаза E — Обновление корневого индекса

1. Просканируй `specification/absolut/` — найди все разделы с `index.md`.
2. Перегенерируй `specification/absolut/index.md` — только ссылки на существующие разделы с кратким описанием.
3. Добавь дату последнего обновления.

### Фаза F — Отчёт

Сообщи пользователю:
- Какие разделы сгенерированы / обновлены.
- Какие файлы созданы в каждом разделе.
- Что не было создано (нет данных в коде) — с пояснением.

## Вызов

```
/spec-absolut-init <функциональность>   — сгенерировать раздел для конкретной бизнес-функциональности
/spec-absolut-init all                  — обнаружить все функциональности и сгенерировать разделы для каждой
```

Примеры:
```
/spec-absolut-init receive              — документация по функциональности «Поступление»
/spec-absolut-init write-off            — документация по функциональности «Списание»
/spec-absolut-init auth                 — документация по функциональности «Аутентификация»
/spec-absolut-init payments             — документация по функциональности «Платежи»
/spec-absolut-init all                  — все функциональности проекта
```

## Идемпотентность и обновление

- При повторном вызове существующие файлы **перезаписываются** актуальным содержимым из кода.
- `index.md` всегда перегенерируется на основе фактически существующих файлов.
- Удалённые из кода сущности **удаляются** из спецификации при обновлении раздела.
- При обновлении одного раздела — остальные разделы не затрагиваются.

## Принципы

| Принцип | Описание |
|---------|----------|
| **Только факты из кода** | Никаких предположений, домыслов, пересказов README. Каждый факт подтверждён файлом исходного кода. |
| **Для агента** | Документация должна давать агенту полный контекст для самостоятельной разработки: что есть, как устроено, где лежит. |
| **Источники** | Ключевые факты сопровождаются указанием файла-источника (относительный путь от корня проекта). |
| **Безопасность** | Секреты, пароли, токены, приватные ключи НИКОГДА не включаются в документацию. |
| **Универсальность** | Скилл работает с любым стеком: Java, Kotlin, TypeScript, Python, Go, Rust, C# и т.д. Шаблоны адаптируются под обнаруженный стек. |
| **Приоритет SQL** | Имена таблиц и колонок из SQL-миграций приоритетнее имён полей в ORM-сущностях. |
| **Навигация** | Каждый файл содержит `[← Назад](index.md)` или `[← Назад](../index.md)`. Корневой `index.md` содержит только ссылки на разделы. |
| **Бизнес-группировка** | Разделы = бизнес-функциональности, не технические слои. Внутри раздела — технические файлы. |
| **Чтение перед записью** | Перед написанием нового раздела **обязательно** прочитай все существующие разделы в `specification/absolut/`, чтобы понимать текущий контекст, избежать дублирования и обеспечить согласованность. |
| **Неприкосновенность других разделов** | При генерации/обновлении раздела **никогда** не изменяй содержимое файлов других разделов (кроме корневого `index.md`). |
| **Перекрёстные ссылки** | Если в текущем разделе нужно сослаться на сущность, таблицу или сервис, подробно описанные в другом разделе, используй относительные ссылки на файлы этого раздела (например, `[см. Entity в разделе receive](../receive/data-model.md)`) вместо дублирования информации. |

## Граничные случаи

| Ситуация | Действие |
|----------|----------|
| Функциональность не найдена в коде | Сообщить пользователю; предложить похожие по имени функциональности |
| У функциональности нет API (внутренний процесс) | `api.md` не создаётся |
| У функциональности нет своих таблиц | `db.md` не создаётся |
| У функциональности нет REST-интеграций | `rest-integration.md` не создаётся |
| У функциональности нет Kafka | `kafka-integration.md` не создаётся |
| У функциональности нет планировщиков | `scheduler.md` не создаётся |
| Одна таблица используется несколькими функциональностями | Документировать таблицу в каждом разделе, где она задействована |
| Один сервис обслуживает несколько функциональностей | Документировать в каждом разделе только релевантные методы сервиса |
| Огромное количество DTO (>20 для одной функциональности) | Разбить `data-model.md` на файлы по типам: `request-dto.md`, `response-dto.md`, `entities.md` |
| Нет файла сборки | Определить стек по расширениям файлов и импортам; пометить «стек определён эвристически» |
| Вызов `all` на большом проекте | Сгруппировать по пакетам/модулям, создать раздел для каждой бизнес-группы |
