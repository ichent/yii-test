# /spec-absolut-init — Абсолютная спецификация frontend-проекта

Генерирует и поддерживает в актуальном состоянии **полную техническую документацию** frontend-проекта в `specification/absolut/`, организованную по **бизнес-функциональностям**.
Документация предназначена для использования AI-агентом при дальнейшей разработке, поэтому содержит максимально точные и структурированные факты из кода.

> **Вариант скилла.** Это frontend-вариант `spec-absolut-init`. Он использует то же имя и тот же вызов, что backend-вариант (`spec-absolut-init_default`), поэтому в один проект устанавливается **только один из них**. Если нужны оба (монорепо с backend и frontend) — переименуй один из вариантов, например в `spec-absolut-init-frontend`, и обнови раздел «Вызов».

---

## Назначение

Абсолютная спецификация — это **единый источник правды** о текущем состоянии frontend-приложения, извлечённый из кода и организованный по бизнес-функциям. Она отвечает на вопросы:

- Что делает конкретная бизнес-функциональность в UI?
- Какие страницы/роуты её обслуживают?
- Какие компоненты, хуки/composables и сторы задействованы?
- Какие вызовы к бэкенду выполняет клиент, включая realtime-подписки?
- Какие формы, валидации, состояния и навигационные потоки связаны с функциональностью?

---

## Вход / выход

- **Вход:** корень репозитория проекта; аргумент — имя бизнес-функциональности (например, `auth`, `catalog`, `cart`, `checkout`, `profile`) или `all`.
- **Выход:** файлы в `specification/absolut/<функциональность>/` + обновлённые `index.md`.

---

## Структура выходных файлов

```
specification/absolut/
├── index.md                              # Корневой индекс — ТОЛЬКО ссылки на разделы
├── <функциональность-1>/
│   ├── index.md                          # Индекс раздела + краткое описание + ссылки на файлы
│   ├── pages.md                          # Страницы / роуты, связанные с функциональностью
│   ├── components.md                     # UI-компоненты и их контракты
│   ├── business.md                       # Хуки, сторы, бизнес-правила UI, состояния
│   ├── data-model.md                     # Types, interfaces, enums, схемы валидации
│   ├── api-integration.md                # REST и GraphQL-вызовы к бэкенду
│   ├── realtime.md                       # WebSocket / SSE / подписки / polling
│   ├── forms.md                          # Формы, поля, submit, UX ошибок
│   ├── navigation.md                     # Навигационные потоки, guards, redirects
│   └── i18n.md                           # Ключи переводов, локали, форматы
├── <функциональность-2>/
│   └── ...
└── ...
```

> **Гибкость:** ни один файл раздела не обязателен, кроме `index.md`. Создавай только те файлы, для которых найдены данные в коде. Отсутствие данных — не повод придумывать содержимое; отметь это в отчёте.

Шаблоны всех файлов и правила извлечения — в [assets/templates.md](assets/templates.md). Прочитай его перед генерацией.

---

## Единственный источник факта

Один факт документируется **в одном файле**. В остальных — только ссылка. Это правило приоритетнее полноты отдельного файла.

| Факт | Файл-владелец | В остальных файлах |
|------|---------------|--------------------|
| Список роутов, пути, layouts, режим рендеринга | `pages.md` | ссылка на `pages.md` |
| Props / Inputs / события компонентов | `components.md` | только имя компонента |
| Локальный state компонента | `components.md` | — |
| Состояния приложения и условия переходов | `business.md` | `pages.md` перечисляет состояния экрана без условий |
| Бизнес-правила UI, обработка ошибок | `business.md` | ссылка на `business.md` |
| Types, interfaces, enums | `data-model.md` | только имя типа |
| Правила валидации (схемы) | `data-model.md` | `forms.md` ссылается на схему |
| Состав полей формы, defaults, UX ошибок | `forms.md` | — |
| Контракты REST / GraphQL-операций, кэш и инвалидация | `api-integration.md` | только имя операции |
| Realtime-соединения, события, polling | `realtime.md` | ссылка на `realtime.md` |
| Условия guard'ов, redirect'ы, правила доступа | `navigation.md` | `pages.md` указывает только имя guard'а |
| Текст переводов, локали, форматы | `i18n.md` | остальные файлы указывают только ключ i18n |

## Как определить бизнес-функциональность

Скилл получает имя функциональности от пользователя. Для поиска связанного кода:

1. **По имени:** ищи директории, модули, файлы, содержащие имя функциональности или его синонимы (например, `auth` → `login`, `signin`, `session`; `cart` → `basket`, `lineItems`).
2. **По роутам:** найди страницы/роуты, относящиеся к функциональности.
3. **По компонентам:** найди компоненты экранов и фич-компоненты функциональности.
4. **По цепочке зависимостей:** от страницы/роута → к компонентам → к хукам/composables/сторам → к API-клиентам → к типам. Собери всю цепочку.
5. **По типам:** найди types/interfaces/schemas, используемые в страницах, компонентах и API-вызовах функциональности.
6. **По API:** найди HTTP-, GraphQL- и realtime-вызовы (fetch, axios, RTK Query, React Query, SWR, Apollo, WebSocket, SSE), инициируемые из функциональности.

> **Не сливай смежные функциональности.** Синонимы расширяют поиск, но если пользователь запросил `cart`, а в проекте есть отдельный `checkout` — это разные разделы. Объединяй только код, который физически принадлежит запрошенной функциональности.

При вызове с `all`:
1. Просканируй все роуты/страницы и feature-модули проекта.
2. Сгруппируй их по бизнес-функциональностям (по директориям `features/`, именам, доменной принадлежности).
3. Сгенерируй раздел для каждой обнаруженной функциональности.

## Алгоритм выполнения

### Фаза A — Анализ проекта

1. **Определи технологический стек:** прочитай файлы сборки/манифесты (`package.json`, `pnpm-workspace.yaml`, `turbo.json`, `angular.json`, `nuxt.config.*`, `next.config.*`, `vite.config.*`, `svelte.config.*` и т.д.). Определи фреймворк UI, роутер, state-менеджер, HTTP/GraphQL-клиент, библиотеку форм и валидации, realtime-транспорт, i18n.
2. **Определи структуру проекта:** просканируй дерево каталогов. Определи расположение pages/app routes, features, components, hooks/composables, stores, api/services, types, форм, файлов переводов.
3. **Проверь существующую спецификацию:** просканируй `specification/absolut/` — определи какие разделы уже существуют.
4. **Прочитай шаблоны:** [assets/templates.md](assets/templates.md).

### Фаза B — Идентификация функциональности

Если аргумент — **имя функциональности:**
1. Ищи код, связанный с этой функциональностью: по именам директорий, модулей, страниц, компонентов, хуков.
2. Проследи цепочку: роут/страница → компоненты → хуки/сторы → API-клиенты → types/schemas.
3. Собери все связанные формы, guards, enums, схемы валидации, realtime-подписки, ключи переводов.

Если аргумент — `all`:
1. Просканируй все роуты/страницы и feature-модули проекта.
2. Сгруппируй по бизнес-функциональностям (по `features/`, доменам, именам).
3. Выполни Фазу B для каждой обнаруженной функциональности.

### Фаза C — Сбор данных (read-only)

Для каждой функциональности собери данные для всех файлов:

1. **pages.md:** роуты и страницы — пути, layouts, имена guard'ов, загрузка данных, состояния экрана.
2. **components.md:** feature/page-компоненты — props, события, зависимости, локальный state.
3. **business.md:** хуки, composables, сторы, бизнес-правила UI, переходы состояний, обработка ошибок.
4. **data-model.md:** types, interfaces, enums, схемы валидации, маппинг API ↔ UI.
5. **api-integration.md:** REST-вызовы и GraphQL-операции, кэш/инвалидация, места вызова.
6. **realtime.md:** WebSocket/SSE-соединения, подписки, входящие и исходящие события, polling-интервалы.
7. **forms.md:** формы, состав полей, defaults, submit-сценарии, UX ошибок.
8. **navigation.md:** пользовательские потоки, guards, redirects, deep links.
9. **i18n.md:** namespace и ключи переводов функциональности, локали, форматирование.

> **Важно:** читай файлы исходного кода напрямую. Не делай предположений — документируй только то, что подтверждено кодом.

### Фаза D — Генерация документации

1. Создай директорию `specification/absolut/<функциональность>/` если не существует.
2. Сгенерируй файлы по шаблонам из [assets/templates.md](assets/templates.md). Создавай только файлы, для которых найдены данные.
3. В каждом файле укажи **источник** (относительный путь к файлу кода) для ключевых фактов.
4. Проверь соблюдение правил из раздела «Единственный источник факта» — замени дублирующийся текст ссылками.
5. Создай/обнови `index.md` раздела со ссылками на фактически созданные файлы.

### Фаза E — Обновление корневого индекса

1. Просканируй `specification/absolut/` — найди все разделы с `index.md`.
2. Перегенерируй `specification/absolut/index.md` — только ссылки на существующие разделы с кратким описанием.
3. Добавь дату последнего обновления.

### Фаза F — Отчёт

Сообщи пользователю:
- Какие разделы сгенерированы / обновлены.
- Какие файлы созданы в каждом разделе.
- Что не было создано (нет данных в коде) — с пояснением.

## Вызов

```
/spec-absolut-init <функциональность>   — сгенерировать раздел для конкретной бизнес-функциональности
/spec-absolut-init all                  — обнаружить все функциональности и сгенерировать разделы для каждой
```

Примеры:
```
/spec-absolut-init auth                 — документация по функциональности «Аутентификация»
/spec-absolut-init catalog              — документация по функциональности «Каталог»
/spec-absolut-init cart                 — документация по функциональности «Корзина»
/spec-absolut-init checkout             — документация по функциональности «Оформление заказа»
/spec-absolut-init profile              — документация по функциональности «Профиль»
/spec-absolut-init all                  — все функциональности проекта
```

---

## Идемпотентность и обновление

- При повторном вызове существующие файлы **перезаписываются** актуальным содержимым из кода.
- `index.md` всегда перегенерируется на основе фактически существующих файлов.
- Удалённые из кода сущности **удаляются** из спецификации при обновлении раздела.
- При обновлении одного раздела — остальные разделы не затрагиваются.

## Принципы

| Принцип | Описание |
|---------|----------|
| **Только факты из кода** | Никаких предположений, домыслов, пересказов README. Каждый факт подтверждён файлом исходного кода. |
| **Для агента** | Документация должна давать агенту полный контекст для самостоятельной разработки UI: что есть, как устроено, где лежит. |
| **Источники** | Ключевые факты сопровождаются указанием файла-источника (относительный путь от корня проекта). |
| **Безопасность** | Секреты, пароли, токены, приватные ключи, значения credentials из env НИКОГДА не включаются в документацию — только имена переменных. |
| **Универсальность** | Скилл работает с любым frontend-стеком: React, Next.js, Vue, Nuxt, Angular, Svelte, SvelteKit и т.д. Шаблоны адаптируются под обнаруженный стек. |
| **UI-контракты** | Приоритет у фактических props, роутов, типов и API-вызовов из кода, а не у дизайн-описаний. |
| **Один факт — одно место** | Каждый факт документируется в файле-владельце (см. таблицу выше), в остальных файлах — только ссылка. |
| **Навигация** | Каждый файл содержит `[← Назад](index.md)` или `[← Назад](../index.md)`. Корневой `index.md` содержит только ссылки на разделы. |
| **Бизнес-группировка** | Разделы = бизнес-функциональности, не технические слои (не «components», не «hooks»). Внутри раздела — технические файлы. |
| **Чтение перед записью** | Перед написанием нового раздела **обязательно** прочитай все существующие разделы в `specification/absolut/`, чтобы понимать текущий контекст, избежать дублирования и обеспечить согласованность. |
| **Неприкосновенность других разделов** | При генерации/обновлении раздела **никогда** не изменяй содержимое файлов других разделов (кроме корневого `index.md`). |
| **Перекрёстные ссылки** | Если в текущем разделе нужно сослаться на тип, компонент или API, подробно описанные в другом разделе, используй относительные ссылки (например, `[см. AuthStore в разделе auth](../auth/business.md)`) вместо дублирования информации. |

## Граничные случаи

| Ситуация | Действие |
|----------|----------|
| Функциональность не найдена в коде | Сообщить пользователю; предложить похожие по имени функциональности |
| У функциональности нет своих роутов (встраиваемая фича) | `pages.md` не создаётся; точки встраивания указать в `components.md` |
| У функциональности нет своих компонентов (только логика) | `components.md` не создаётся |
| У функциональности нет своих типов | `data-model.md` не создаётся |
| У функциональности нет форм | `forms.md` не создаётся |
| У функциональности нет API-вызовов | `api-integration.md` не создаётся |
| У функциональности нет realtime и polling | `realtime.md` не создаётся |
| У функциональности нет отдельной навигационной логики | `navigation.md` не создаётся |
| В проекте нет i18n, строки захардкожены | `i18n.md` не создаётся; отметить факт хардкода строк в отчёте |
| Только shared UI без бизнес-логики | Не выделять в отдельный раздел; документировать в разделах-потребителях при необходимости |
| Один стор/хук обслуживает несколько функциональностей | Документировать в каждом разделе только релевантные методы/селекторы |
| Один API-клиент используется несколькими функциональностями | Документировать в каждом разделе только релевантные операции |
| Огромное количество компонентов (>20 для одной функциональности) | Разбить `components.md` на файлы: `page-components.md`, `feature-components.md` |
| Нет package.json / конфига фреймворка | Определить стек по расширениям файлов и импортам; пометить «стек определён эвристически» |
| Вызов `all` на большом проекте | Сгруппировать по features/modules/routes, создать раздел для каждой бизнес-группы |
| Монорепо с apps/ + packages/ | Специфицировать app-entry и связанные feature-пакеты; указывать источники с путями от корня репозитория |
